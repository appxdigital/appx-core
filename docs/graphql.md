# GraphQL (read API)

AppX Core exposes a **read-only GraphQL API** generated from your Prisma schema. Every query runs through the same ABAC proxy as REST, so row-level filtering, field omission, and nested-relation filtering all apply automatically — a caller only ever receives rows and fields their role is permitted to read.

> **Scope:** **read only** — `find`, `get`, `count`. Writes (create/update/delete) are **not** exposed; use the REST CRUD endpoints. See [limitations.md](./limitations.md).

> **Recommended for reads.** For querying, filtering, and **pagination** (native `take` / `skip` / `cursor`) prefer GraphQL over the generated CRUD list endpoint — one request can select several models, alias repeated queries, and pull nested relations in a single round-trip. Enable it on your main queryable models (one line per module, below); keep REST for writes.

---

## The endpoint

The GraphQL server is mounted at **`POST /graphql`** (Apollo; open `GET /graphql` in a browser for the Apollo Sandbox). New projects (`appx-core create`) get it wired in `app.module` by default. To add it to an existing project, register the module once:

```ts
import { GraphqlModule } from '@appxdigital/appx-core';

@Module({ imports: [ /* … */ GraphqlModule ] })
export class AppModule {}
```

The server is always valid even before any model is exposed (it ships a trivial `_appxCore` root field), so `/graphql` is live from the start.

## Exposing a model (opt-in, per module — one line)

GraphQL is **off per model** until you opt in. Every generated module ships a commented, copy-paste-ready opt-in; enabling a model is one import + one provider line, with **no resolver file to write or maintain**:

```ts
import { Module } from '@nestjs/common';
import { PrismaModule } from '../../prisma/prisma.module';
import { AlbumController } from './album.controller';
import { AlbumService } from './album.service';
import { AlbumResolver } from '../../generated/album/graphql';   // generated by `appx-core generate`

@Module({
  imports: [PrismaModule],
  controllers: [AlbumController],
  providers: [
    AlbumService,
    AlbumResolver,   // ← add = exposed; remove = not exposed
  ],
})
export class AlbumModule {}
```

`AlbumResolver` is a ready-to-register resolver class emitted by the deploy-safe pass (`appx-core generate`) at `src/generated/album/graphql.ts` — regenerated from the schema, never hand-edited. (The same file exports the underlying `AlbumGraphql` bundle if you'd rather build the resolver yourself via the exported `CoreGraphqlResolver`.)

## Queries — `find` / `get` / `count`

Each exposed model contributes **one root field** (its camelCase name) whose fields are the three read operations. Naming is uniform across every model, so it's predictable:

| Field | Prisma | Returns |
|---|---|---|
| `find(where, orderBy, take, skip, …)` | `findMany` | a list |
| `get(where, …)` | `findFirst` | a single record, or `null` |
| `count(where)` | `count` | `Int` |

```graphql
query {
  album {
    find(where: { year: { equals: 2024 } }, take: 20) { id title }
    get(where: { id: { equals: 1 } }) { id title }
    count(where: { year: { equals: 2024 } })
  }
}
```

Because `find`/`get`/`count` live on the per-model namespace (not the root), the names repeat freely across models and never collide.

### Multiple things in one request + aliases

A single query can select many models at once, and aliases let you repeat an operation with different arguments — all in one round-trip:

```graphql
query {
  album {
    recent:  find(where: { year: { equals: 2024 } }) { id title }
    classics: find(where: { year: { lt: 1990 } })     { id title }
    total:   count
  }
  artist { get(where: { id: { equals: 7 } }) { name } }
}
```

Each selected field resolves independently through the proxy (its own authorized query), so multiplexing never weakens enforcement. `count` is filtered too — it counts only the rows the caller may read, never the table total.

### Nested relations

Select **to-one** relations inline — they return a single record, and the selection compiles into one Prisma `select` (no N+1):

```graphql
query {
  album {
    get(where: { id: { equals: 1 } }) {
      title
      artist { name }          # to-one relation — OK
    }
  }
}
```

**To-many relations are not nested-selectable** (`album.tracks`, `project.tasks`). Nested lists have no pagination, so an inline list could return unbounded rows. Query the list at the **top level** instead, where pagination applies:

```graphql
query {
  album  { get(where: { id: { equals: 1 } }) { title } }
  tracks: track { find(where: { albumId: { equals: 1 } }, take: 20, orderBy: { id: asc }) { id title } }
}
```

You can still get a bounded **count** of a to-many relation via `_count` (`album { get { _count { tracks } } }`), and you can **filter** by a to-many relation in `where` (`some` / `every` / `none`) — that returns the parent rows, not the list.

## Filtering, sorting & pagination

`find` / `get` take the generated Prisma-style arguments; `count` takes `where`.

- **Pagination** (`find`): `take`, `skip`, `cursor: { <uniqueField>: … }`, `distinct: [field]`.
- **Sorting** (`find`): `orderBy: { field: asc | desc }` — including nested to-one, `orderBy: { artist: { name: asc } }`.

**`where` operators**, by field type:

| Field type | Operators |
|---|---|
| `String` | `equals`, `not`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `contains`, `startsWith`, `endsWith`, `mode: insensitive` |
| `Int` / `Float` / `Decimal` / `BigInt` | `equals`, `not`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte` |
| `Boolean` | `equals`, `not` |
| `DateTime` | `equals`, `not`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte` |
| enum | `equals`, `not`, `in`, `notIn` |
| nullable field | any of the above, plus `null` / `{ equals: null }` / `{ not: null }` |
| to-one relation | `is: { … }`, `isNot: { … }` (a nested `where`) |
| to-many relation | `some: { … }`, `every: { … }`, `none: { … }` |
| logical | `AND`, `OR`, `NOT` |

The **generated GraphQL input type is the authoritative allowlist** — an operator that isn't on a field's filter type is a GraphQL error, so unknown operators are rejected before they run. Browse the exact set per field in the Apollo Sandbox (`GET /graphql`).

Two framework rules on top of that:

- **You can only filter/sort by fields your role can read.** A `where`/`orderBy` on a `@Role`-hidden column is rejected with `403`. The **only** exception is a **bare-null presence check** — `{ field: null }`, `{ field: { equals: null } }`, `{ field: { not: null } }`, or `{ NOT: { field: null } }` — which reveals only whether a value is set. **Any value-bearing predicate on a hidden field still `403`s**, including `{ field: { not: "x" } }` and `{ field: { equals: "x" } }` — anything that compares against a real value. `orderBy` and `distinct` on a hidden field are always rejected (no presence exception).
- **A malformed value returns a clean `400`.** `createdAt: { gt: 2024 }` (a number where a date is expected) is a `400`, never a `500` or a leaked Prisma error.

## What the caller can and cannot see (ABAC)

All three operations route through `PrismaService.getModelDelegate`, so the rules in `permissions.config.ts` apply exactly as they do for REST reads (see [permissions.md](./permissions.md)). Concretely:

- **Unauthorized rows are not returned.** `find` returns only rows the role may read; `get` returns `null` for a row the caller can't access even if asked for by unique field; `count` counts only accessible rows.
- **Restricted fields are omitted.** A column the role can't read (`/// @Role(...)`) comes back **`null`** even though the GraphQL type exposes it — at the top level *and* nested. (`prisma-nestjs-graphql` types every scalar; the proxy is what strips the values.)
- **Inaccessible nested records are filtered.** If a nested relation points at a record the caller can't read, that relation is filtered out — a to-many yields only the visible rows; an inaccessible to-one drops the parent row. You can hold access to a record while a record it links to is withheld.
- **You can only filter/sort by fields you can read.** A `where` / `orderBy` / `distinct` that references a field the role can't read (`@Role`) is rejected with `403` — top level or nested. The **only** exception is a **bare-null presence check** in `where` (`{ field: null }` / `{ field: { equals: null } }` / `{ field: { not: null } }` / `{ NOT: { field: null } }`) — it reveals only whether a value is set, so `hasX` / `isDeleted` work without a bypass. A **value-bearing** predicate still `403`s (even `{ field: { not: "x" } }`), and `orderBy`/`distinct` on a hidden field have no presence exception.
- **Anonymous callers are `GUEST`.** With no valid `Authorization: Bearer <jwt>` (or session), the request is a GUEST; a model with no GUEST rule is denied.

> Because relation records and fields are filtered by ABAC, "empty / null" means "not visible to you", not "does not exist". Design queries and UI accordingly.

Always let the generated resolver serve the data — a custom resolver that reaches the **raw** Prisma client bypasses ABAC.

## Not available yet

- **Mutations** (create/update/delete) — use REST.
- **Full `aggregate`** (sum/avg/min/max/groupBy) — only `count` is exposed today.

---

## After changing the schema

Re-run `appx-core generate`. It refreshes the Prisma client, GraphQL types, DTO bases, and the per-model `graphql.ts` bundles under `src/generated/**`. Your module opt-in lines are untouched.
